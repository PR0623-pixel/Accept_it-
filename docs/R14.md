# R14 — 게임 설정 기본값/범위 검증

## 목적과 적용 기준
- 기준 소스: 사용자가 제공한 `Accept_it-(20261118-201150).zip` + R13 패치. R01~R13 기능 유지.
- 핵심: **기본값·최솟값·최댓값을 `RoomSettingsPolicy` 한곳에서 관리**하고, 저장 전 모든 설정값을 검증한다.
- **향후 설정 변경 가능**: 지금 상수로 관리하는 수치는 추후 게임 기획/프론트엔드 UI와 합의하면 수정할 수 있다. 절대 불변의 규칙이 아니다.

## 현재 적용 값

| 설정 (API 이름) | 현재 기본값 | 최소 | 최대 | 단위·근거 | 상태 |
|---|---:|---:|---:|---|---|
| `cardsPerItem` | 3 | 1 | 5 | 개수 1단위, `frontend/src/types.ts` | 프론트 기준 |
| `itemSeconds` | 300 | 180 | 1200 | 60초 단위(현재 DB는 분 저장), 프론트 UI step=60 | 프론트 범위 + 서버 저장 제약 |
| `maxItems` | 3 | 1 | 5 | 개수 1단위, `frontend/src/types.ts` | 프론트 기준 |
| `speechSeconds` | 120 | 1 | 3600 | 초, 프론트에는 기본값 120초 상수만 존재 | **서버 임시 기술 상한** |
| `rebuttalSeconds` | 60 | 1 | 3600 | 초, 프론트에는 기본값 60초 상수만 존재 | **서버 임시 기술 상한** |

`1~3600초`는 **프론트와 합의된 기획 범위가 아니며**, 0·음수·비현실적으로 큰 수를 임시로 막는 검증용 범위다. 추후 게임 설계·UI 결정에 따라 교체한다. 위 두 시간도 서버에는 수정 가능한 값으로 저장되지만, 프론트 UI에서는 현재 고정 상수다.

## 동작
- `PUT /api/rooms/{roomCode}/settings`에 5개 필드를 모두 요청한다. 모든 필드는 필수다. 유효하면 204, 저장 후 전원 Ready=false.
- 범위 초과·누락 또는 `itemSeconds` 60초 단위 불일치는 **400**과 `{ "code": "BAD_REQUEST", "message": "필드명..." }`로 응답한다. 실패 시 DB 변경 및 Ready 초기화 없음.
- 방 상태가 WAITING이 아니면 409 `ALREADY_STARTED`, Host가 아니면 403 `NOT_HOST`. 기존 R13 규칙 그대로.
- `POST /api/rooms` 구형 선택적 `maxCardCount`(1~5) 및 `turnTimeLimit`(3~20분)도 같은 범위로 검사한다. 빈 값은 기본값 3장/5분.
- `GET /api/rooms/{roomCode}`에서는 다섯 설정을 모두 조회한다.

## `itemSeconds`의 60초 단위에 관하여
- `frontend/src/types.ts`에서 UI 조절 간격은 60초이고, 기존 DB `room.turn_time_limit`은 **분 단위 정수**다. 그래서 지금은 479초 같은 값을 정확히 저장할 수 없어 서버에서 400을 반환한다.
- **`mockServer.ts`는 step을 강제하지 않고 min/max로 clamp**한다. 프론트의 목 서버와 실제 백엔드 동작 차이가 있으므로 통신 담당자와 조정해야 한다.
- 향후 임의 초 입력을 지원하려면 DB를 초 단위 컬럼으로 전환하는 **새 Flyway 마이그레이션**, 엔티티/서비스 매핑 수정 및 프론트 UI 정책 변경이 필요하다. **이미 적용된 V1~V5 파일을 수정하면 안 된다.**

## 추후 변경해야 하는 항목 (사용자 요청)
1. Host가 프론트에서도 `speechSeconds`·`rebuttalSeconds`를 조정하게 할지, 각 항목의 최솟값·최댓값·조절 간격을 팀과 확정.
2. 합의된 값에 맞춰 `RoomSettingsPolicy` 상수와 프론트 `SETTINGS_LIMITS`/UI를 함께 수정; 필요한 경우 새 DB 마이그레이션 생성.
3. 프론트 `RoomSettings`와 WebSocket `UPDATE_SETTINGS`는 현재 3개만 전송하므로, 5개 연동 시 새 필드와 기본값 처리 계약을 합의해야 함. **이번 R14에서는 프론트 파일을 수정하지 않음**.
4. 실제 발언/반론 제한시간 로직에서는 프론트 고정 상수가 아닌 Room의 저장 설정을 사용하도록 G/D/B 단계에서 연결.
5. 앞서 확정한 **1~2명이어도 역할 선택 후 Ready 가능** 정책은 유지. 아직 구형 프론트 `types.ts`/mock 설명에 3명 미만 Ready 불가로 적혀 있어 후속 동기화 필요.
6. 역할 선택 REST `POST /api/rooms/{roomCode}/role`에서 `roomCode`를 서비스에 전달하지 않는 기존 문제는 **요청에 따라 R14에서 건드리지 않음**.

## 검증
```powershell
.\gradlew.bat clean test
.\gradlew.bat bootRun
```

- 방 생성 후 기본값: 3/300/3/120/60 (`maxItems/itemSeconds/cardsPerItem/speechSeconds/rebuttalSeconds`).
- 설정 허용 경계값: `cardsPerItem=1,5`, `maxItems=1,5`, `itemSeconds=180,1200` 성공.
- 거부: `cardsPerItem=0,6`, `maxItems=0,6`, `itemSeconds=179,1201,479`, `speechSeconds=0,3601`, `rebuttalSeconds=0,3601`, 필드 누락.
- 실패 요청 이후 값/Ready가 그대로인지 확인. 성공 후에만 전원 Ready=false.
- 생성 API의 구형 `turnTimeLimit`은 3~20분, `maxCardCount`는 1~5.
- WebSocket `UPDATE_SETTINGS` 및 실제 사용자 식별·인증은 별도 후속 단계.
