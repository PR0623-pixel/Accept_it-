# R09 — 로비 역할과 물품별 찬반 입장 분리

## 목표
- 로비 역할은 `NONE`(미선택), `GUEST`(객원), `MODERATOR`(사회자)만 사용한다.
- `PRO`/`CON`은 객원이 **물품마다 새로 선택하는** 입장(`Stance`)이다.
- Host는 별도 권한(`Room.hostPlayer`)이며 어떤 로비 역할도 선택할 수 있다.
- 방 생성/입장 시 새 참가자의 역할은 `NONE`, 물품별 입장은 `null`, Ready는 `false`다.

## 변경 내용
1. `LobbyRole` enum(`NONE/GUEST/MODERATOR`), `Stance` enum(`PRO/CON`) 추가.
2. `Player.role`은 `LobbyRole`, `Player.stance`는 nullable `Stance`로 분리.
3. `RoomService.getLobby()`가 실제 로비 역할을 반환한다(기존 `MODERATOR` 외 `NONE`으로 표시하던 임시 로직 제거).
4. 기존 `/api/rooms/ready`는 **수동 검증용 임시 REST 역할 선택**으로 유지된다. `NONE/GUEST/MODERATOR`만 허용하며 역할 선택 시 Ready는 `false`로 초기화한다. 이후 WebSocket `SET_ROLE`, `SET_READY`로 교체/정리한다.
5. 기존 `/api/debate`는 컴파일 호환성을 위해 로비 역할 GUEST + 현재 `stance`로 화자를 판단한다. **물품별 VOTE 엔진이나 다음 물품 시 stance 초기화 로직은 아직 구현되지 않았다.**
6. `GameStartService`는 토론 시작의 찬성 진영을 미리 확정하지 않는다(`currentTurnRole=null`). 기존 게임 시작 경로는 후속 게임 진행 엔진 및 R16 구현 전까지 프론트 계약을 모두 충족하지 않는다.
7. Flyway `V4__separate_lobby_role_and_item_stance.sql`: 기존 `role` 값 `PRO/CON`을 `GUEST`로, `NULL`을 `NONE`으로 데이터 보존 변환한다. 과거 로비 찬반을 현재 물품 투표로 **간주하지 않고** `stance`는 `NULL`로 둔다. 기존 마이그레이션 V1~V3 수정 금지.

## 적용 전
- **변경된 enum과 DB migration은 반드시 함께 적용**한다. 코드만 적용하거나 DB만 수정하면 서버 시작 시 JPA `validate` 오류가 날 수 있다.
- 로컬에 중요 데이터가 있다면 DB 백업을 권장한다. Flyway는 부팅 시 자동 실행된다.
- 실행 전에 `src/main/resources/db/migration/`에 V4가 하나만 있는지 확인한다.

## Swagger 검증
1. `POST /api/rooms` `{ "nickname": "Host" }` → `200`, roomCode/playerId 반환.
2. `POST /api/rooms/{roomCode}/join` `{ "nickname": "Guest" }` → `200`.
3. `GET /api/rooms/{roomCode}` → 두 참가자 role은 `NONE`, Ready는 `false`, Host는 `isHost=true`.
4. `POST /api/rooms/ready` `{ "playerId": <실제ID>, "role": "GUEST" }` → `200`. (현재는 역할만 변경, Ready=false.)
5. `GET /api/rooms/{roomCode}` → 해당 플레이어 role은 `GUEST`.
6. 다른 플레이어를 `MODERATOR`로 선택 → 로비 조회 시 `MODERATOR`, Host 권한은 유지.
7. `role="NONE"` → 로비 조회에서 `NONE`, Ready=false.
8. `role="PRO"`, `role="CON"` → `400 BAD_REQUEST`. (찬반은 투표 단계에서만 선택.)
9. DB에서 `SELECT id, player_name, role, stance, is_ready FROM player;` → 신규 참가자의 stance는 `NULL`.
10. `./gradlew.bat clean test` (PowerShell: `.\gradlew.bat clean test`) → 전체 테스트 통과.

## 후속 단계
- R10: `MODERATOR` 1명, `GUEST` 2명 역할 인원 제한(현재 중복 배정 방지 기능은 미구현).
- R11: 별도 Ready / Ready 취소.
- R12: 역할 변경/Ready 정책 완성.
- R16: 시작 가능 조건/Host 시작 권한.
- WebSocket: `SET_ROLE`, `SET_READY`, `ROOM_STATE` 및 `VOTE` 통신, 각 물품 시작 시 stance 초기화.

**주의:** `GET /api/rooms/{roomCode}`는 로비 확인용 REST이며, 프론트가 요구하는 WebSocket `ROOM_STATE`의 전체 JSON 구조(stance/hasVoted 포함)를 아직 구현한 것이 아니다.
