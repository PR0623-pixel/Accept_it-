# S02 — 서버 타이머 시스템 구현

기준: `Accept_it-(20261120-192027).zip` + **S01 게임 상태 전환 공통화 패치** 적용본.

## 1. 구현 범위

- `@EnableScheduling` 활성화 및 `GameTimerService` 주기 실행 (기본 250ms, 설정 `acceptit.game.timers.poll-ms`).
- 방별 메모리 상태에서 **물품 토론 제한 시각 `itemEndsAt`**을 확인하여 `finishDebateIfActive()`를 한 번만 호출.
- 일반 발언과 승인된 반론의 **`speech.endsAt`** 시각 만료 시 발언권만 회수 (`speech=null`).
- DB의 방 설정 `speechSeconds`, `rebuttalSeconds`를 `RoomGameState` 생성 시 전달 (이전 120/60 하드코딩 제거).
- 상태 변경 직후 토론 종료 시 `ROOM_STATE` + 각 사용자 `HAND`, 발언 종료 시 `ROOM_STATE`를 WebSocket 전송.
- 해당 방이 종료되어 Store에서 삭제된 경우 자동 검사 제외. 라운드 전환 및 RESULT 진입 시 기존 타이머가 다음 라운드를 종료하지 못함.
- 서버 시각으로 토론 또는 발언 제한이 경과한 직후, 폴링 사이에 도착한 발언/반론/채팅 요청도 유효 기간을 검사. 특히 발언 시한을 넘긴 요청은 DB 카드 마킹 전에 차단.
- 테스트: `RoomGameStateTimerTest` (10), `GameTimerServiceTest` (3), `GameTimerWebSocketTest` (3) + S01 테스트 회귀.

## 2. 확정한 이번 단계의 시간 정책

| 상황 | 동작 |
|---|---|
| 물품 토론 `itemEndsAt` 도달 | 진행 중인 발언·반론보다 우선하여 토론 종료 → `MODERATOR_DECISION` |
| 일반 발언 `speech.endsAt` 도달 | `speech=null`, 현재 물품의 토론은 계속 |
| 승인된 반론의 `speech.endsAt` 도달 | 반론 발언권 회수, 토론은 계속 |
| 반론 심사 대기 중 기존 발언 제한 도달 | 원래 발언권만 회수, 반론 심사 요청은 유지 (사회자 판정 또는 물품 제한 시간까지) |
| 물품 토론 종료 당시 미처리 반론 | S01의 공통 종료 로직이 예약된 반론 카드 반환 |
| 중복 타이머 틱·수동 종료와 경합 | 상태 변경은 최대 한 번, 추가 WebSocket 메시지 없음 |
| 다른 물품에 진입 | 신규 물품의 투표 완료 후 `itemEndsAt` 재설정, 이전 제한 시각 무시 |

**시간 제한 정책의 우선순위:** 물품 토론 제한 시간이 발언 종료보다 우선한다. 따라서 마지막 카드로 시작한 발언이라도 물품 전체 시간이 끝나면 종료될 수 있다. 카드 소진을 감지해서 종료할 때 발언을 마무리하게 하는 규칙은 **S03**에서 구현한다.

새 DB 테이블 및 Flyway 마이그레이션은 필요하지 않다.

## 4. 패치 적용

1. **S01을 먼저 적용하고**, 최신 브랜치에서 필요한 로컬 변경을 커밋 또는 백업한다.
2. ZIP 안의 경로를 프로젝트 루트에 그대로 덮어쓴다. `git status`로 변경 범위를 확인한다.
3. Windows PowerShell에서 테스트 실행:

```powershell
.\gradlew.bat clean test
.\gradlew.bat test --tests "*RoomGameStateTimerTest" --tests "*GameTimerServiceTest" --tests "*GameTimerWebSocketTest" --tests "*RoomGameStateDebateFinishTest" --tests "*LobbyWebSocketHandlerDebateFinishTest"
```

4. Docker DB를 시작한 후 `bootRun` 실행:

```powershell
docker compose up -d
.\gradlew.bat bootRun
```

5. WebSocket으로 MODERATOR 1명 + GUEST 2명을 구성하고 찬반을 다르게 투표하여 `DEBATE` 진입. 일반 발언에 배분된 카드를 사용해 발언을 시작한 후 설정한 `speechSeconds`가 끝나면 **추가 요청 없이** `ROOM_STATE.speech=null`을 받는지 확인한다. 승인된 반론에도 동일하게 적용한다.
6. 물품 제한 시간 `itemSeconds`가 지나면 `MODERATOR_DECISION`과 재전송된 각 사용자 손패를 확인한다. 프론트에서 Mock 모드 대신 실제 백엔드로 연결해야 검증할 수 있다.

**테스트 설정 주의:** `itemSeconds`는 현재 정책상 최소 180초, 60초 단위이다. 자동 테스트는 인위적인 현재 시각을 주입하므로 수동 대기가 필요 없다. `speechSeconds`, `rebuttalSeconds`는 서버 설정에서 1~3600초 범위를 사용한다.

## 5. 현재 제한 및 다음 작업

- **S03:** 한쪽 진영 카드 소진 자동 감지 및 발언 완료 후 토론 종료 연결. (이번 S02에서 미구현)
- **S04:** 상태/카드 사용 실패에 따른 DB 트랜잭션 롤백 및 완전한 정합성 보강. 이번 변경은 만료 발언 요청의 DB 사전 마킹만 차단한다.
- **S06:** 서버 재시작 뒤 게임 상태와 남은 타이머 복구. 현재 `RoomGameStateStore`는 프로세스 메모리이므로 재시작 시 소실된다.
- **S09:** 오래된 WebSocket 핸들러 중복 및 연결 인증 정리.
- 메모리에서 바뀐 타이머 상태는 게임 Store의 현재 상태다. 영속 타이머 이벤트 로그나 푸시 재시도 큐는 이번 단계에 포함하지 않는다.
- 별도 시스템 장애로 Scheduler가 정지하면 타이머 역시 동작하지 않는다. 폴링 주기 이상의 밀리초 단위 정밀도는 보장하지 않는다.

## 6. 빌드 검증 상태

패치 작성 환경에서 Java 21은 확인했으나, Gradle 9.9.1 배포본을 설치할 수 없는 네트워크 제한으로 Gradle 테스트를 실제 수행하지 못했다. 신규 테스트 코드는 작성하였지만 **PASS로 표시하지 않는다.** Windows 개발 환경에서 테스트와 실제 3인 WebSocket 통합 검증을 반드시 실행해야 한다.
