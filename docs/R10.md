# R10 — 로비 역할별 인원 제한

## 정책 / 프론트 계약
- 로비 역할은 `NONE`, `GUEST`, `MODERATOR`이며 물품별 입장 `PRO/CON`과 독립적이다.
- `MODERATOR`는 **최대 1명**, `GUEST`는 **최대 2명**이다. `NONE`은 미선택으로 제한 없음.
- Host 여부는 역할 슬롯을 점유하거나 면제하는 특별 권한이 아니다. Host도 동일하게 역할을 선택한다.
- 인원 초과는 **HTTP 409** + `{ "code": "ROLE_FULL", "message": "해당 역할 자리가 가득 찼습니다." }`로 응답한다. 이후 WebSocket `SET_ROLE`도 같은 ERROR 코드 사용.
- 기존 역할과 동일하게 재선택할 수 있으며 본인은 인원 계산에서 제외한다.
- `NONE` 선택이나 다른 역할로의 이동으로 이전 역할 자리를 반납할 수 있다.
- 성공한 역할 선택은 Ready를 `false`, 물품별 stance를 `null`로 초기화한다(R09 정책). **정원 초과로 실패하면 원래 상태 유지.**
- `WAITING`에서만 변경 가능하며 이미 시작된 게임은 `409 CONFLICT`.

## 동시 요청 안정성
1. `PlayerRepository.findRoomIdByPlayerId`는 Player 엔티티를 로딩하지 않고 방 ID만 조회한다.
2. `RoomRepository.findByIdForUpdate`는 R05에서 사용하던 방 행의 **PESSIMISTIC_WRITE** 잠금을 획득한다.
3. 잠금 획득 후 `PlayerRepository.findByRoomForUpdate`로 참가자 목록을 잠금 조회한다.
4. 역할 인원을 계산하고 변경하여 트랜잭션이 커밋될 때까지 방 잠금을 유지한다.

MySQL의 기본 `REPEATABLE READ`에서는 처음 조회한 데이터의 스냅샷이 유지될 수 있다. 그래서 잠금 전에 Player 전체를 가져와 역할을 집계하지 않고, 잠금 후 참가자 명단을 **FOR UPDATE**로 읽어 최신 커밋 상태를 사용한다. 참가자는 최대 3명이라 목록 조회도 간단하다.

## Swagger 수동 검증
1. `POST /api/rooms` `{ "nickname": "Host" }` → `roomCode`, `playerId` 확인.
2. `POST /api/rooms/{roomCode}/join`으로 두 명 더 입장해 총 3명 구성.
3. `POST /api/rooms/ready` `{ "playerId": <Host ID>, "role": "MODERATOR" }` → `200`.
4. 다른 플레이어가 `MODERATOR` 선택 → `409 ROLE_FULL`.
5. 나머지 두 명이 각각 `GUEST` 선택 → 모두 `200`.
6. 이미 `MODERATOR`인 Host가 동일 역할 재선택 → `200`, 불필요한 정원 오류 없음.
7. 역할을 `NONE`으로 변경하면 자리 반납. 빈 자리를 다른 플레이어가 선택하면 `200`.
8. `GET /api/rooms/{roomCode}` 조회: 사회자 최대 1, 객원 최대 2, Host 여부 독립.
