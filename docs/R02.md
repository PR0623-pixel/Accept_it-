# R02 — 방 생성과 Host 지정

## 목표

- R01에서 검증한 `nickname`을 방 생성 요청에서도 필수로 받음.
- 방 생성자 `Player`를 생성하고 `Room.hostPlayer`로 연결함.
- Host 권한과 로비 역할은 별개: 생성 직후 `Player.role == null`, `Player.isReady == false`.
- 프론트 계약 `POST /api/rooms {"nickname":"홍길동"}` → `{"roomCode":"ABC123","playerId":"15"}`.
- `playerId`는 기존 `Long` PK를 문자열로 직렬화. UUID로 DB를 변경하지 않음.

## 변경 파일

- `entity/Room.java`: Host FK 연관관계 추가.
- `db/migration/V3__add_room_host_player.sql`: 기존 Room은 null 허용하는 호환 마이그레이션.
- `dto/RoomCreateRequest.java`, `dto/RoomEnterResponse.java`: 프론트 계약 추가.
- `service/RoomService.java`: @Transactional로 room -> player -> room.hostPlayer 저장.
- `controller/RoomController.java`: Swagger + JSON 응답.
- Service / Controller 테스트 추가.

## 데이터베이스 검증

Spring Boot 실행 전에 MySQL이 켜져 있고 DB 설정이 로드되어 있어야 함.

```sql
SELECT r.id, r.room_code, r.host_player_id,
       p.id AS player_id, p.player_name, p.role, p.is_ready
FROM room r
LEFT JOIN player p ON p.id = r.host_player_id
ORDER BY r.id DESC
LIMIT 10;
```

새 방에서는 `host_player_id == player_id`가 참이고 `player_name`이 정규화된 이름이어야 함.
기존 R01 테스트용 방은 `host_player_id`가 null일 수 있음 (기존 데이터 자동 추정 금지).

## Swagger

`POST /api/rooms`:

```json
{"nickname":"  홍길동  "}
```

예상 응답 HTTP 200:

```json
{"roomCode":"ABC123","playerId":"15"}
```

실제 방 코드는 임의의 6자리 대문자 영숫자이고 Player ID는 DB에서 발급한 값을 문자열로 반환함.

## 범위 밖 / 다음 작업

- **R03**: 6자리 방 코드의 중복 충돌 재시도 (현재는 DB UNIQUE 제약에 의존).
- **R04**: join 시 WAITING 검사, `RoomEnterResponse`로 응답 변경, 404 에러 명세.
- **R05**: 동시 참가 최대 3명 보장.
- **R09**: `LobbyRole.NONE/GUEST/MODERATOR` 완전 분리. 기존 Player.role의 PRO/CON 데이터 모델은 그 단계에서 전환.
- **R13/R14**: 프론트의 3개 게임 설정 항목 계약. 현재 레거시 room 필드에 기본 카드 수 3, 제한시간 5분을 저장.
- **X01**: `ErrorResponse.errorMessage`와 프론트 `message`의 이름 차이 조율.
- **WebSocket**: 아직 미구현. 실제 프론트의 /room 페이지는 상태 소켓 없이는 정상 작동하지 않음.
- R01 체크리스트의 같은 방 중복 닉네임 정책은 별도 기획 결정을 기다림.

### 보안 및 데이터 주의

- 실제 비밀정보를 포함한 `.env`와 데이터베이스 스냅샷은 절대 커밋하지 않음.
- 이미 생성된 방의 Host를 임의로 기존 Player 1명으로 배정하지 않음.
- Host 권한 검증은 R15에서 개발. R02에서는 `room.hostPlayer.id`를 단일 진실의 원천으로 저장.
