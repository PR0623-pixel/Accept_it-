# R03 — 간소화된 방 코드 발급 및 중복 방지

## 적용 기준

- R01과 R02가 **적용된 상태**에 덮어쓰기. 이전에 제공한 복잡한 R03 패치는 적용하지 않는다.
- 프론트엔드 `POST /api/rooms` 요청/응답은 그대로 유지한다.
- 랜덤 6자리 `A-Z`, `0-9` 코드 생성.
- DB `existsByRoomCode` 사전 검사 후, 이미 사용 중이면 최대 5회 재발급.
- `Room` 및 `Player(Host)` 저장은 **하나의 `@Transactional`** 로 처리한다.
- DB의 `UNIQUE(room_code)` 제약은 기존 V1에 있으므로 새 Flyway 마이그레이션이 필요 없다.

## 의도적으로 생략한 복잡성

- 별도 `RoomCreationPersistenceService` 없음.
- SQLState·MySQL 에러 번호·제약 이름 분석 없음.
- DB INSERT 시점에서 **동시에 생성된 다른 방과 우연히 코드가 겹치는 경우**에는 재시도하지 않고 DB 예외가 발생하며 트랜잭션이 롤백된다. 이 희귀한 상황을 자동 복구하는 것이 필요해지면 추후 추가한다.
- 재시도는 이미 DB에 저장된 코드가 사전 검사에서 발견된 경우에만 적용된다.

## 응답 및 실패 처리

- 정상: `200 {"roomCode":"ABC123","playerId":"15"}` (실제 값은 변동)
- 5회 연속 사전 중복: `503 {"code":"ROOM_CODE_GENERATION_FAILED","errorMessage":"..."}`
- 검증이 끝나지 않은 구형 로비 `PRO/CON` 역할 코드는 R09에서 변경한다. R03에서는 역할 변경 없음.

## 검증

```powershell
.\gradlew.bat clean test
.\gradlew.bat bootRun
```

Swagger `POST /api/rooms`에 `{"nickname":"Host"}`를 여러 번 제출하고, 각 응답의 roomCode 형식 확인.

```sql
SELECT room_code, COUNT(*) AS cnt
FROM room
GROUP BY room_code
HAVING COUNT(*) > 1;
```

중복이 없으면 위 쿼리는 0행을 반환한다. 재시도 분기는 `RoomServiceCodeTest`에서 모킹으로 검증한다.
