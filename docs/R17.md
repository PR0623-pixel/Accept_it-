# R17 — 로비 상태 변경 이벤트

## 1. 범위

R16 완료 이후 R17에서는 **입장/퇴장/역할/Ready/설정** 변경이 DB에 성공적으로 저장되면, 해당 방의 모든 WebSocket 세션으로 최신 `ROOM_STATE`를 보냅니다. 서버가 상태의 원천이며, diff 대신 전체 스냅샷을 사용합니다.

- 전송 프로토콜: **일반 WebSocket**, STOMP 사용하지 않음
- 연결 URL: `ws://localhost:8080/ws/rooms/ABC123?playerId=11`
- 개발 프론트(Vite, 기본 `localhost:5173`)는 기존 `/ws` 프록시를 통해 8080으로 연결
- 프론트 `.env`: `VITE_USE_MOCK=false`
- 연결 직후: `ROOM_STATE` → `HAND`(현재는 `[]`) → `CHAT_HISTORY`(현재는 `[]`)
- R17은 LOBBY만 다룸. 다른 게임 단계의 개인화(HAND/stance 마스킹), 채팅, 재연결 안정화, 보안은 후속 단계에서 확장.

## 2. 처리 흐름

1. 기존 Swagger REST API 또는 연결된 WebSocket에서 로비 변경 명령 수신
2. `RoomService`가 검증하고 WAITING 방을 잠근 상태에서 저장
3. 서비스가 `LobbyChangedEvent`를 트랜잭션 안에서 발행
4. `@TransactionalEventListener(AFTER_COMMIT)`가 커밋 성공 시만 동작
5. 이벤트 리스너가 새 읽기 전용 트랜잭션에서 `RoomService.getLobby` 조회
6. `LobbyRoomStateMapper`로 프론트 `RoomState` 전체 구조 생성 후 방별 `ROOM_STATE` 전송

예외나 트랜잭션 롤백이 발생하면 알림을 보내지 않습니다. R16의 읽기 전용 시작 조건 확인도 알림을 생성하지 않습니다.

### 연결 후 WebSocket 요청

| type | payload | 동작 |
|---|---|---|
| `SET_ROLE` | `{ "role": "GUEST" }` | 기존 R10/R12 검증/Ready 초기화; 커밋 후 방 상태 전송 |
| `SET_READY` | `{ "ready": true }` | 1~2명도 Ready 가능; 커밋 후 방 상태 전송 |
| `UPDATE_SETTINGS` | `{ "maxItems": 4, "itemSeconds": 480, "cardsPerItem": 2 }` | Host만 변경; 발언·반론 시간 보존, 모든 Ready 해제, 커밋 후 전송 |
| 그 외 | `{...}` | `ERROR {"code":"INVALID", "message":"..."}` (G/AI/C/D/W 단계 구현 예정) |

**주의**: WebSocket `SET_ROLE`은 기존 R09 서비스 메서드를 사용하고, `RoomController`의 임시 REST 역할 변경 API 및 추후 수정을 위해 보류한 `roomCode` 전달 문제는 손대지 않았습니다.

### ROOM_STATE 예시

```json
{
  "type": "ROOM_STATE",
  "payload": {
    "roomCode": "ABC123", "serverTime": 1795050000000, "phase": "LOBBY",
    "players": [{
      "id": "11", "nickname": "방장", "role": "MODERATOR", "ready": true,
      "stance": null, "hasVoted": false, "isHost": true
    }],
    "settings": {"maxItems": 3, "itemSeconds": 300, "cardsPerItem": 3},
    "currentItem": null, "itemEndsAt": null, "speech": null,
    "lastSpeakerId": null, "pendingRebuttal": null,
    "effect": null, "results": []
  }
}
```

`serverTime`은 실제 현재 epoch milliseconds이며, `players`는 방 인원 전체(최대 3인)입니다. 현재 `speechSeconds`, `rebuttalSeconds`는 DB에 저장되지만 프론트 `RoomSettings` JSON의 3항목에는 포함하지 않습니다. 두 값의 설정 범위는 R14 문서의 추후 조정 사항을 유지합니다.

### 퇴장 / 오류

- 손님 퇴장: 그 손님 자신의 소켓에는 `ERROR PLAYER_NOT_IN_ROOM` 후 종료, 다른 참가자에게는 최신 `ROOM_STATE` 전송
- Host 퇴장: 방+플레이어 DB 삭제 후 방의 **모든** 연결에 `ERROR ROOM_NOT_FOUND` 후 종료
- 없는 방에 접속: `ERROR ROOM_NOT_FOUND` 후 종료
- 다른 방/잘못된 플레이어 ID 연결: `ERROR PLAYER_NOT_IN_ROOM` 후 종료
- 요청 검증 실패: **요청자에게만** `ERROR {code,message}`, 방 전체 `ROOM_STATE` 전송하지 않음
- 브라우저 WebSocket 연결만 끊긴 경우: 방에서 자동 퇴장시키지 않음. 같은 플레이어 ID로 재접속 가능

## 3. 설치 및 검증

패치를 프로젝트 루트에 덮어쓴 후:

```powershell
.\gradlew.bat clean test
.\gradlew.bat bootRun
```

R17 관련 테스트:

```powershell
.\gradlew.bat test --tests "*LobbyRoomStateMapperTest" --tests "*LobbyWebSocketHandlerTest" --tests "*LobbyChangedListenerTest" --tests "*RoomServiceLobbyEventTest"
```

**Swagger 검증**: Host와 손님 1~2명을 REST로 입장시킨 뒤 `GET /api/rooms/{roomCode}`로 플레이어 ID 확인. 프론트 `VITE_USE_MOCK=false` 연결이나 브라우저 개발자 콘솔 WebSocket으로 연결. Swagger에서 `POST /api/rooms/{roomCode}/role`, `.../ready`, `PUT .../settings`를 바꿔도 연결된 브라우저에 `ROOM_STATE`가 전달되는지 확인.

브라우저 콘솔 최소 테스트:

```javascript
const ws = new WebSocket('ws://localhost:8080/ws/rooms/ABC123?playerId=11');
ws.onmessage = e => console.log(JSON.parse(e.data));
ws.onopen = () => ws.send(JSON.stringify({type:'SET_ROLE', payload:{role:'GUEST'}}));
```

다른 방에 동시에 연결하면 변경된 방의 이벤트만 받아야 합니다.

## 4. 후속 과제 및 한계

1. **신원 보안 미완성**: URL의 `playerId`는 위조 가능합니다. 방 소속 검증을 하지만 인증 토큰이 없어 공개 서비스에 배포하면 안 됩니다. W/T 단계에서 발급·검증 가능한 토큰과 Origin 정책을 추가해야 합니다. 현재 모든 Origin을 허용하는 것은 로컬 개발 전용입니다.
2. **인메모리 세션 관리**: 단일 서버 기준. 여러 서버 인스턴스에서 방별 이벤트를 전달하려면 Redis pub/sub 등 별도 브로커가 필요합니다.
3. **프론트 mock 정책 차이**: mock은 아직 Ready 인원 3명 미만 제한 및 모두 Ready면 자동 시작 동작이 있지만, 사용자 확정 규칙은 1~2명도 Ready 가능, 실제 게임 시작은 G03. 프론트 mock 업데이트 필요.
4. **W01/W02**: W01에서 연결 인증·재연결·오류처리를 정식 정리하고, W02에서 라운드/판정 등 다른 이벤트로 채널을 확장합니다. 현재 R17은 LOBBY 한정 기초 WS 전송입니다.
5. **G03**: R16 검사와 실제 게임 세션 시작을 하나의 트랜잭션으로 묶기 전까지 `SET_READY`가 모두 true가 되어도 방은 LOBBY에 남습니다.
6. **발언·반론 시간**: R14의 임시 범위 1~3600초를 그대로 유지하고 추후 변경 가능하도록 합니다.
7. **서버 전체 테스트**는 이 환경에서 Gradle 의존성 미확보 시 실행하지 못할 수 있으므로 로컬 실행 결과로 검증합니다.
