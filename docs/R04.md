## 적용 기준
- `frontend/BACKEND_CONTRACT.md` / `frontend/src/api/rest.ts` / `frontend/src/types.ts`
- 기준 코드: R01 + R02 + R03(간소화) 패치 완료 상태
- 구현 범위: REST 입장 요청, 성공 응답 DTO, 입장 상태 검증, 프론트 공통 오류 형식
- R05(동시 입장 시 3명 정원 무결성), R09(로비 역할), W 단계(WebSocket 브로드캐스트) 제외

## REST 계약

`POST /api/rooms/{roomCode}/join` with JSON `{"nickname":"홍길동"}`

| 상황 | HTTP | 응답 |
|---|---|---|
| 정상 입장 | 200 | `{"roomCode":"ABC123","playerId":"15"}` |
| 없는 방/잘못된 코드 | 404 | `{"code":"ROOM_NOT_FOUND","message":"방을 찾을 수 없습니다."}` |
| 방 정원 3명 | 409 | `{"code":"ROOM_FULL","message":"방이 가득 찼습니다."}` |
| 시작/종료된 방 | 409 | `{"code":"ALREADY_STARTED","message":"이미 시작된 방입니다."}` |
| 닉네임 오류 | 400 | `{"code":"INVALID_NICKNAME","message":"..."}` |

- `playerId`: DB Long PK를 **JSON 문자열**로 반환한다. 프론트엔드 `Player.id`와 동일한 표현.
- 방 코드: 앞뒤 공백 정리 후 대문자로 변환. 6자리 영숫자 이외는 ROOM_NOT_FOUND.
- 닉네임: R01 `NicknameValidator` 재사용, 양끝 공백 제거, 1~10자.
- 서버 내부 `WAITING` 상태만 프론트 로비(`LOBBY`)에서 입장 가능하도록 매핑.
- Host는 R02에서 생성한 플레이어를 유지; Join 플레이어 `role=null`, `ready=false`.
- 기존 `?playerName=...` 사용법은 **임시 호환**. 프론트의 정식 입장 방식은 JSON 요청.
- 글로벌 `ErrorResponse`의 JSON 필드를 **`errorMessage` → `message`**로 변경: 프론트는 `err.message`를 그대로 표기하므로 필요. Unity/레거시 클라이언트가 있다면 영향 점검.
- DB 스키마/Flyway 수정 없음. R05 이전에는 동시에 마지막 자리를 신청하면 일시적인 4인 입장 가능성이 있음.
- WebSocket `ROOM_STATE` 전송은 이 패치가 수행하지 않음. WS 단계에서 통합 예정.

### SQL (실제 DB 확인)

```sql
SELECT r.room_code, r.status, r.host_player_id, COUNT(p.id) AS player_count
FROM room r LEFT JOIN player p ON p.room_id = r.id
GROUP BY r.id, r.room_code, r.status, r.host_player_id
ORDER BY r.id DESC LIMIT 10;
```

### 참고
- 기존 방 코드 충돌 및 R02 Host 생성 로직은 변경하지 않음.

- R05에서 `Room` 잠금 기반 정원 동시성 방어를 적용할 계획.
