# S05 — 게임 종료 및 DB 상태 정합성

기준 소스: `Accept_it-(20261121-003911).zip` (S01~S04 검증 완료본). 적용 브랜치: `feat/game-flow-stabilization`.

## 목적과 확정 정책

- 사회자 `DECIDE_ITEM`이 **마지막 물품**을 판정하면 `room.status = FINISHED`, 게임 `phase = RESULT`가 된다.
- 다음 물품이 있으면 `room.current_item_id`만 다음 물품으로 옮기고, `status = IN_PROGRESS`, 게임 `phase = VOTING`을 유지한다.
- **현재 DB 물품 ID와 메모리에서 판정하려는 물품 ID가 일치해야** 판정을 반영한다.
- DB 상태 변경/트랜잭션 커밋이 실패하면 `results`, `phase`, `currentItem`을 변경하지 않고 요청자에게 WebSocket `ERROR`를 보낸다.
- 한 방의 `DECIDE_ITEM` 전체 흐름을 `synchronized (state)`로 직렬화하여 중복 판정을 방지한다.
- 성공한 판정에서만 `ROOM_STATE` → 각 참가자의 개인 `HAND` → `CHAT_HISTORY`(빈 배열)를 순서대로 전송한다. RESULT 화면에서도 이전 손패가 남지 않는다.
- `RESULT` 단계에서는 재판정, 새 투표, 발언, 반론, 카드 사용, 사회자 채팅, 타이머 전환이 불가능하다.
- 구형 `POST /api/debate/{roomId}/finish`가 실시간 게임 상태를 우회해 DB만 `FINISHED`로 바꾸던 동작은 **409 Conflict**로 차단한다. 실시간 종료는 WebSocket `END_DEBATE`, 전체 게임 완료는 마지막 `DECIDE_ITEM`만 사용한다. 기타 REST 토론 경로 정리는 S09에서 수행한다.

## 3인 수동 검증: 마지막 물품

1. 서버 헬스체크 `Invoke-RestMethod http://127.0.0.1:8080/actuator/health` → `UP`.
2. 방 Host(MODERATOR), 객원 2명(GUEST)을 준비하고 `maxItems=1`, `itemSeconds=180`으로 방 설정 후 모두 Ready.
3. 세 참가자가 Postman Desktop으로 `ws://127.0.0.1:8080/ws/rooms/방코드?playerId=각ID` 연결.
4. Host `START_GAME` → `VOTING`. 객원 2명 모두 `PRO`를 투표하면 토론을 생략하고 `MODERATOR_DECISION`으로 이동하므로 카드 데이터 준비 없이 검증하기 좋다.
5. 사회자만 `{"type":"DECIDE_ITEM","payload":{"accept":true}}` 전송.
6. 3명이 모두 `ROOM_STATE.phase = RESULT`, `results` 길이 1, `accepted=true`, 이어서 빈 `HAND` 및 `CHAT_HISTORY`를 수신하는지 확인.
7. MySQL에서 아래 SQL 실행. 방의 `status`가 `FINISHED`인지 확인.
8. 같은 `DECIDE_ITEM` 재전송 → 요청자 `ERROR`, 중복 결과 없음. 게임 끝난 후 `START_SPEECH`, `REQUEST_REBUTTAL`, `VOTE`, 사회자 `SEND_CHAT`도 거부되어야 한다.
9. 연결을 끊고 **서버를 재시작하지 않은 상태**에서 다시 접속 → 기존 `RESULT` 및 결과 목록 수신. 서버 재시작 후 복구는 S06 범위다.

```sql
SELECT id, room_code, status, current_item_id
FROM room
WHERE room_code = '실제방코드';
```

MySQL 접속은 프로젝트 `application.yml` 기본값상 **Windows `localhost:3307`**이며, DB 이름/인증정보는 `.env`에 설정된다. 자격증명은 공유하지 않는다.

## 3인 수동 검증: 중간 라운드

1. 새 방 `maxItems=2`로 시작. 객원 두 명이 동일한 찬반을 투표하여 `MODERATOR_DECISION` 진입.
2. 첫 `DECIDE_ITEM` 실행 → 서버 `room.status = IN_PROGRESS`, 현재 물품이 두 번째 물품으로 변경되고 인메모리 `phase = VOTING`.
3. 첫 결과만 목록에 남고 `HAND` 및 `CHAT_HISTORY`는 비워진다.
4. 두 번째 물품에서도 객원 두 명의 같은 찬반 투표 후 사회자가 `DECIDE_ITEM` → `FINISHED`/`RESULT`, `results` 2개.
5. 이미 끝난 방에 추가 `DECIDE_ITEM`을 전송해도 결과가 늘어나지 않아야 한다.

## 실패·동시성 검증 (자동 테스트)

- DB 반영이 예외로 실패하면 인메모리 `phase = MODERATOR_DECISION`, `results`는 이전대로, 다른 참가자에게 잘못된 RESULT 발송 없음.
- 실패 요청을 다시 보내면 정상이 된 경우에 한 번만 결과 반영.
- 2개의 최종 `DECIDE_ITEM` 요청이 같은 방에 동시에 들어와도 DB 진입 1회, 결과 1개.
- 이전 라운드의 물품 ID로 DB 완료 처리 요청 시 변경 거부.
- 기존 REST `/api/debate/{roomId}/finish` 경로는 409이고 DB 방 상태를 변경하지 않음.

## 범위와 제약

- `Room.status` 및 `current_item_id`의 DB 전환은 트랜잭션으로 보호하지만, **인메모리 게임 상태와 DB는 하나의 원자적 트랜잭션이 아니다**. 일반적인 DB 오류/중복 요청은 방지하되, DB 커밋 직후 JVM이 강제 종료되는 간극은 S06의 결과 영속화·재접속 복구로 다룬다.
- **물품별 승인/기각 결과(`results`)는 현재 메모리에만 존재**한다. DB에 결과 기록을 추가하는 Flyway 변경과 서버 재시작 복구는 S06의 별도 작업이다.
- DB의 `current_item_id`는 FINISHED 이후에도 *마지막으로 판정한 물품*을 가리킨다. 클라이언트 `ROOM_STATE.currentItem`은 RESULT에서 `null`이며 의도된 표현 차이다.
- 이번 단계는 정식 카드 콘텐츠를 만들거나 배분 로직을 바꾸지 않는다. 팀이 추후 DB에 카드 내용을 입력하는 계획을 유지한다.
- 개발 환경에서 Gradle 배포본 네트워크 접근이 막혀 Java/JUnit 전체 테스트는 직접 실행할 수 없었다. Windows 로컬에서 `clean test`와 실제 MySQL 상태 확인을 완료한 후 S05를 완료 처리한다.
