# R05 — 3인 정원 및 동시 입장 보호

## 범위
- R04 완료 상태에서 적용. 기존 REST JSON, 오류 코드, 닉네임 규칙을 유지한다.
- `RoomRepository.findByRoomCodeForUpdate()`에 JPA `PESSIMISTIC_WRITE` 잠금을 추가한다.
- `RoomService.joinRoom()`의 `@Transactional` 안에서 방 행 잠금 → WAITING 확인 → 인원 수 조회 → 플레이어 저장을 수행한다.
- MySQL InnoDB의 행 잠금으로 **같은 방**의 동시 입장을 순차 처리한다. 서로 다른 방은 별개 행이다.
- DB 마이그레이션, 새 인프라, 새 예외 클래스는 없다.

## 로컬 확인
1. R04 패치까지 적용된 브랜치에서 `git status --short`로 변경 파일 확인 후 덮어쓴다.
2. `./gradlew.bat clean test` 실행.
3. `./gradlew.bat test --tests "*RoomServiceJoinTest"` 실행.
4. Swagger에서 Host 1명 생성 → 2명 입장 성공 → 4번째 입장 HTTP 409, `ROOM_FULL` 확인.
5. MySQL: `SELECT r.room_code, COUNT(p.id) AS members FROM room r LEFT JOIN player p ON p.room_id=r.id WHERE r.room_code='실제방코드' GROUP BY r.id, r.room_code;` 결과 3 확인.
6. `IN_PROGRESS` 방은 기존대로 HTTP 409 `ALREADY_STARTED`인지 확인.

## 동시 입장 검증 (선택)
Host 1명만 있는 테스트 방에 3개 이상의 HTTP 입장 요청을 병렬로 전송하고, 성공 2건/`ROOM_FULL` 나머지 및 최종 DB 인원 3명을 확인한다. 동시 요청은 실제 서버와 MySQL에서 확인해야 한다. JUnit 단위 테스트는 락 호출 순서를 검증할 뿐 DB 행 잠금의 동시성 자체를 증명하지 않는다.

## 주의
- MySQL 테이블 엔진은 InnoDB여야 한다.
- 같은 DB를 공유하는 여러 Spring Boot 인스턴스에서도 행 잠금이 작동한다.
- DB 락 대기 시간 초과 등은 일반 DB 오류로 남는다. 공모전 규모에서는 추가 재시도/분산 락을 도입하지 않는다.
- 역할 변경/게임 시작 등의 다른 트랜잭션과 정합성은 해당 후속 단계에서 검증한다.
