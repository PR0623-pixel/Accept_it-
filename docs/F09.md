# F09 — 서버 정상 실행 및 헬스체크 구현

> **프로젝트:** AcceptIt 백엔드  
> **기준 자료:** `Accept_it-(20261111-154413).zip` 및 F09 진행 중 공유된 실행 결과  
> **기술 환경:** Java 21, Spring Boot 4.1.2, Gradle, MySQL 8.0(Docker Compose), Spring Data JPA, Flyway  
> **현재 판정:** **구현 반영 완료 / 최종 스모크 테스트 재검증 필요**

## 1. 목적 및 범위

F09의 목적은 게임 기능을 변경하지 않고 백엔드 서버와 MySQL의 상태를 HTTP로 확인하는 것이다. Spring Boot Actuator의 기본 Health 기능을 사용하며, DB 전용 상태 검사는 Health Group으로 분리한다.

- 전체 서버 상태: `GET /actuator/health`
- MySQL 상태: `GET /actuator/health/database`
- 운영 정보 보호: Health 이외의 Actuator 엔드포인트는 HTTP에 노출하지 않으며, Health 응답에서 세부 컴포넌트 정보를 숨긴다.
- 검증 자동화: PowerShell 스크립트 `scripts/verify-f09.ps1`

## 2. 구현 내용 및 파일

| 파일 | 변경 또는 확인 내용 |
| --- | --- |
| `build.gradle` | `spring-boot-starter-actuator` 의존성 추가 |
| `src/main/resources/application.yml` | Health 엔드포인트 공개 범위 및 상세정보 숨김 설정, DB HealthIndicator 활성화, DB 전용 Health Group 추가 |
| `scripts/verify-f09.ps1` | 전체 Health 및 DB 전용 Health Group의 `UP` 상태 확인, 실패 시 종료 코드 1 반환 |
| `docs/F09.md` | F09 구현·검증 기록(본 문서) |

기존 `datasource`, `jpa.hibernate.ddl-auto: validate`, Flyway, OpenAI 설정은 유지되어 있다. 자체 `HealthController`나 커스텀 `HealthIndicator`를 추가하지 않았다.

### 2.1 Gradle 의존성

```groovy
implementation 'org.springframework.boot:spring-boot-starter-actuator'
```

### 2.2 Actuator 설정

현재 `application.yml`에 반영된 내용은 다음과 같다.

```yaml
management:
  endpoints:
    web:
      exposure:
        include: health
  endpoint:
    health:
      show-details: never
      show-components: never
      group:
        database:
          include: db
  health:
    db:
      enabled: true
```

`show-details: never` 및 `show-components: never`는 세부 정보를 외부에 표시하지 않도록 하는 설정이다. `database` 그룹은 기본 DB HealthIndicator인 `db`를 포함한다.

## 3. 엔드포인트 및 기대 결과

| 요청 | 정상 시 기대 결과 | 비고 |
| --- | --- | --- |
| `GET /actuator/health` | HTTP 200, `{"status":"UP"}` | 전체 Health 상태 |
| `GET /actuator/health/database` | HTTP 200, `{"status":"UP"}` | DB 상태만 검사하는 Health Group |
| `GET /actuator/env` | HTTP 404 | Health 이외 관리 엔드포인트 비공개 확인 |
| `GET /api/does-not-exist` | HTTP 404 | F08 공통 예외 응답 회귀 확인 |

상태 검사 결과가 `DOWN`으로 집계되면 일반적인 Actuator 설정에서 HTTP 503을 반환할 수 있다. 단, HTTP 503만으로 장애 원인이 DB라고 확정할 수 없고, 서버가 시작하지 못한 경우에는 연결 자체가 실패할 수 있다.

Health의 `UP`은 등록된 상태 검사가 성공했다는 뜻이며, 모든 게임 API 및 Unity 연동이 정상이라는 뜻은 아니다.

## 4. 진행 과정과 확인된 결과

### 4.1 최초 스모크 테스트: 부분 성공

F09 진행 중 실행한 `scripts/verify-f09.ps1`에서 다음 결과가 공유되었다.

```text
[F09] Checking server health...
[PASS] Health status: UP
[FAIL] F09 health check failed.
원격 서버에서 (404) 찾을 수 없음 오류를 반환했습니다.
```

당시 스크립트는 두 번째 요청으로 `/actuator/health/db`를 사용했다. 따라서 **전체 Health는 `UP`으로 확인됐지만, DB 개별 경로는 404로 실패**했다. 이 404만으로 DB 연결 실패라고 판단할 수는 없다.

### 4.2 경로 및 설정 수정: ZIP에서 확인됨

현재 ZIP의 `application.yml`에는 `management.endpoint.health.group.database.include: db` 설정이 추가되어 있다. `scripts/verify-f09.ps1`의 DB 검사 경로도 다음과 같이 수정되어 있다.

```powershell
-Uri "$baseUrl/actuator/health/database"
```

**단, 변경 후 실제 서버를 재시작하여 `All checks passed.`가 출력됐다는 로그는 아직 제공되지 않았다.** 따라서 현재 F09 전체 스모크 테스트 성공 여부는 **미확인**이다.

### 4.3 자동화 테스트 현황

ZIP에 포함된 `build/test-results/test/`의 XML 결과는 다음과 같다.

| 테스트 클래스 | 실행 | 실패 | 오류 | 건너뜀 |
| --- | ---: | ---: | ---: | ---: |
| `GlobalExceptionHandlerTest` | 2 | 0 | 0 | 0 |
| `OpenAiServiceTest` | 6 | 0 | 0 | 0 |
| **합계** | **8** | **0** | **0** | **0** |

이 결과는 **기존 F08 테스트의 저장된 실행 결과**다. 현재 ZIP에는 F09 전용 JUnit 테스트가 없으며, 본 문서 작성 시 Gradle 또는 Docker를 새로 실행한 것은 아니다.

## 5. 로컬 검증 절차 (Windows / PowerShell)

실제 비밀번호와 API 키는 명령어 출력, 문서, Git 커밋에 포함하지 않는다. `.env`는 Docker Compose의 환경변수 치환에 쓰이며, IntelliJ 또는 `bootRun`으로 시작하는 Spring Boot에는 DB 환경변수를 별도로 전달해야 한다.

### 5.1 MySQL 컨테이너 확인

프로젝트 루트에서 실행한다.

```powershell
docker compose ps
```

필요한 경우 MySQL을 실행한다.

```powershell
docker compose --env-file .env up -d mysql-db
```

### 5.2 Gradle 테스트 및 서버 시작

Spring Boot 실행 프로세스에 `DB_NAME`, `DB_USER`, `DB_PASSWORD` 환경변수가 설정되어 있는지 확인한다. 이후:

```powershell
.\gradlew.bat clean test
.\gradlew.bat bootRun
```

정상 시작 시 확인할 로그 예시:

```text
HikariPool-1 - Start completed.
Initialized JPA EntityManagerFactory
Tomcat started on port 8080
Started AcceptItApplication
```

`bootRun`이 `EXECUTING`으로 유지되는 것은 서버 프로세스가 계속 동작하기 때문이며, 그 자체로 오류가 아니다.

### 5.3 헬스체크 수동 검증

서버를 실행한 상태에서 **다른** PowerShell 터미널에서 확인한다.

```powershell
curl.exe -i http://localhost:8080/actuator/health
curl.exe -i http://localhost:8080/actuator/health/database
curl.exe -i http://localhost:8080/actuator/env
curl.exe -i http://localhost:8080/api/does-not-exist
```

기대값은 3절의 표를 따른다. `/actuator/health/database`가 404라면 `application.yml` 반영 여부 및 서버 재시작 여부부터 확인한다.

### 5.4 스모크 테스트

```powershell
.\scripts\verify-f09.ps1
```

모든 검사 통과 시 기대 출력:

```text
[F09] Checking server health...
[PASS] Health status: UP
[PASS] Database status: UP
[F09] All checks passed.
```

위 내용은 **기대 출력**이며, 최신 ZIP에 대한 실제 성공 로그로 확인된 것은 아니다.

## 6. 보안 및 주의사항

- Actuator의 HTTP 노출은 `health`로 제한한다.
- Health 응답에는 내부 컴포넌트 상세정보를 표시하지 않는다.
- `GET /actuator/env`가 외부에 공개되지 않았는지 확인한다.
- `.env`에는 실제 DB 자격 증명이 있으므로 Git과 팀원 공유용 ZIP에서 제외한다. `.env.example`은 예시값만 포함한다.
- DB 상태 검증을 위해 `docker compose down -v`, `DROP DATABASE` 등 데이터 삭제 명령을 사용하지 않는다.
- `/actuator/health/database`는 DB 상태 점검용이며 인증/공개 범위는 운영 환경에서 별도 검토한다.
