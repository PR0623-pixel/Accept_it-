# R06 — 로비 정보 조회

## 범위
- `GET /api/rooms/{roomCode}`: Swagger 및 백엔드 상태 검증용 로비 스냅샷
- 반환 필드: `roomCode`, `hostPlayerId`, `phase`, `players`, `settings`
- `players`: `id`, `nickname`, `role`, `ready`, `isHost`
- `settings`: `maxItems`, `itemSeconds`, `cardsPerItem`
- 없는 방: HTTP 404 `ROOM_NOT_FOUND` (R04 오류 처리 재사용)

## 프론트엔드와의 관계
프론트 `src/types.ts`의 `RoomState`는 WebSocket `ROOM_STATE`로 전송하는 **더 큰 구조**입니다. 이번 REST DTO는 그 중 로비 필드만 담는 조회 모델이며, 프론트 `src/api/rest.ts`는 이 GET API를 호출하지 않습니다. 따라서 이번 단계만으로 로비 UI 실시간 연동이 완료되는 것은 아닙니다. 추후 WebSocket 구현 시 이 매핑을 재사용·확장해야 합니다.

## 기존 스키마에서 발생하는 임시 제약
- R09 이전에는 DB 역할이 `PRO/CON/MODERATOR`입니다. `MODERATOR`만 `MODERATOR`로 표시하고 나머지는 `NONE`으로 표시합니다. **GUEST로 추정하지 않습니다.** R09에서 실제 `NONE/GUEST/MODERATOR` 모델로 교체해야 합니다.
- `maxItems=5`는 **임시 기본값**입니다. DB에 저장되는 정식 방 설정은 R13/R14에서 구현합니다.
- 기존 `turnTimeLimit`는 분 단위이므로 `itemSeconds = turnTimeLimit * 60`으로 변환합니다.
- `WAITING -> LOBBY`, `FINISHED -> RESULT`이며, `IN_PROGRESS -> VOTING`은 임시 표시입니다. 세부 게임 phase는 G 단계에서 별도 모델로 구현해야 합니다.
- 기존 역할·Ready 선택 API는 수정하지 않습니다.

## 검증
1. `./gradlew.bat clean test`
2. Swagger에서 `POST /api/rooms`로 방 생성 후 `GET /api/rooms/{roomCode}` 호출
3. Host의 `isHost=true`, `ready=false`, `role=NONE` 확인
4. `POST /api/rooms/{roomCode}/join`으로 2명 입장 후 조회 시 players 3명 확인
5. 소문자 방 코드 조회 가능, 없는 코드 조회 시 404 `ROOM_NOT_FOUND` 확인
6. DB의 `maxCardCount`, `turnTimeLimit` 값과 settings 변환 비교

DB 마이그레이션과 프론트엔드 코드는 변경하지 않습니다.
