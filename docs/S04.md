# S04 — 카드·발언·반론 정합성 보강

기준: `Accept_it-(20261120-232549).zip` (S01~S03 적용된 최신 소스)

## 범위

- `START_SPEECH`: 권한, 단계/시각, 발언권 점유, 연속 발언, 손패 소유·사용 여부를 **DB 갱신 전에** 검사
- `REQUEST_REBUTTAL`: 동일 사전 검증 후 DB 카드 사용 처리; 반론 대기 중 중복 요청 차단
- `DECIDE_REBUTTAL(approve=false)`: DB 카드 복구 성공 후 메모리 복구, 요청자 개인 `HAND` 재전송
- 수동 `END_DEBATE` 또는 S02의 전체 토론 시간 만료: 미처리 반론 카드 DB 복구 후 S01 공통 종료 처리
- `SituationCardRepository`: 카드 소유 진영 외 **현재 물품 ID**를 `markUsed`/`restoreUsedCard` 조건에 추가
- 두 객원에게 지급할 손패를 검증 후 한 번에 적용. 카드 부족/중복/배분 오류 시 마지막 투표 롤백, `VOTING` 상태로 재시도 가능
- 동일 방에서 검증·DB 처리·메모리 갱신을 `synchronized (state)`로 직렬화
- 기존 S03의 '한쪽 남은 카드 0장 → 현재 발언·반론 완료 후 종료', 물품별 새 손패 지급 유지

## 3인 WebSocket 수동 검증

Postman Desktop/WebSocket 또는 Chrome 개발자도구를 이용해 사회자(MODERATOR), 객원 PRO/CON 3명을 연결한다. 기존 S03 가이드에 따라 `VOTING → DEBATE`에 진입하고 각 개인 `HAND`에서 실제 `cardId`를 확인한다. 여러 카드를 사용할 수 있도록 `cardsPerItem=2`, `speechSeconds=60`, `rebuttalSeconds=20`을 권장한다.

1. **상대방 카드 / 없는 카드 발언**: PRO가 CON의 카드로 `START_SPEECH` → `ERROR`, PRO 카드 DB·HAND 변동 없음.
2. **중복 발언**: PRO가 유효 카드로 발언한 직후 다른 카드로 `START_SPEECH` → `ERROR(FLOOR_BUSY)`; 나중 카드의 `used` 변경 없음.
3. **중복 요청**: 같은 `START_SPEECH` 두 번 전송 → 한 번만 카드 사용 처리되고 두 번째 `ERROR`.
4. **정상 반론 예약**: PRO 발언 중 CON이 `REQUEST_REBUTTAL` → 본인 `HAND.used=true` 및 DB `situation_card.is_used=1`.
5. **묵살**: 사회자가 `DECIDE_REBUTTAL {"approve":false}` → CON 예약 카드 DB `is_used=0`, CON에만 갱신 `HAND`, 원래 PRO 발언 유지.
6. **승인**: 새 반론을 승인 → 승인된 카드 `is_used=1` 유지, 반론 만료/종료까지 발언권 유지.
7. **수동 종료와 타이머 종료**: 미처리 반론 상태에서 `END_DEBATE` 또는 전체 토론 시간 만료 → 예약 카드 DB 및 HAND 복구, `MODERATOR_DECISION`.
8. **라운드 격리**: 첫 라운드의 `cardId`를 다음 라운드 `START_SPEECH`에 사용 → `ERROR(CARD_NOT_IN_HAND)`, 다음 라운드 손패 변경 없음.
9. **배분 카드 부족**: 향후 팀 등록 DB에 특정 진영의 현재 물품 카드가 모자라면 `VOTING` 상태가 유지되고 마지막 투표자가 재시도 가능해야 함 (일부러 DB를 삭제하는 검증은 테스트 전용 DB에서만 진행).

요청 JSON 예시:

```json
{"type":"START_SPEECH","payload":{"cardId":101}}
```
```json
{"type":"REQUEST_REBUTTAL","payload":{"cardId":201}}
```
```json
{"type":"DECIDE_REBUTTAL","payload":{"approve":false}}
```
```json
{"type":"END_DEBATE","payload":{}}
```

SQL 확인 예시 (테스트 DB의 실제 ID로 교체):

```sql
SELECT sc.id, sc.room_id, sc.procurement_item_id, sc.owner_role, sc.is_used
FROM situation_card sc
WHERE sc.room_id = 123
ORDER BY sc.procurement_item_id, sc.id;
```

## 남은 제약 및 후속 단계

- Spring/JPA 트랜잭션과 인메모리 `RoomGameState`는 하나의 ACID 트랜잭션이 아니다. 일반적인 실패·중복·검증 실패는 사전 검증 및 보상 처리로 막았지만, JVM 강제 종료나 보상용 DB 복구 자체 실패 같은 극단적인 경우는 재조정이 필요하다. 게임 세션의 DB 영속화/재접속 복원은 S05~S06의 별도 범위다.
- 미처리 반론 카드 DB 복구에 실패하면, 손패/DB의 추가 불일치를 방지하기 위해 해당 토론 종료·묵살 처리가 실패하고 이후 재시도한다. 서버 로그를 확인할 것.
- 현재 서버는 시작 시 테스트용 상황 카드를 생성한다. 팀에서 추후 정식 카드 데이터를 DB에 등록하는 구조로의 전환은 별도 작업이다.
- WebSocket의 `playerId` 신원 위조 방지는 S09에서 처리할 보안 과제다.
- 현재 `USE_CARD` 액션은 WebSocket에서 비활성화되어 있다. 본 패치는 실제 사용되는 `START_SPEECH`/`REQUEST_REBUTTAL` 경로를 대상으로 한다.
- 이 작업 환경에서는 Gradle 9.9.1 배포본에 접근할 수 없어 전체 Gradle/JUnit 테스트를 실행하지 못했다. 개발 PC에서 빌드와 DB 통합 검증이 필요하다.
